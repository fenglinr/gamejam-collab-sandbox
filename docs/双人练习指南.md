# 双人练习指南

目标：两个人分别在自己的电脑上提交改动、合并、取得对方的改动，并验证 LFS 资产可以恢复。预计 30～45 分钟；不需要 Godot 或 Blender。

以下 Git 命令可在 Windows PowerShell 或 macOS 终端使用，每段中的命令依次执行。日常也可使用熟悉的图形客户端；LFS 锁先按这里的命令练习。

## 0. 准备账号和权限

仓库所有者在 GitHub 的 Settings → Collaborators 添加朋友，朋友接受邀请。不要共享 GitHub 登录信息。仓库保持 Private；当前没有设置必须由另一人批准才能合并。

每台参与电脑运行：

```sh
git --version
git lfs version
```

缺少 Git 或 LFS 时，先安装对应系统的官方版本。之后克隆远端仓库；已有本地初始仓库的所有者不用再克隆。

```sh
git clone https://github.com/fenglinr/gamejam-collab-sandbox.git
cd gamejam-collab-sandbox
git lfs install --local
git lfs pull
git lfs ls-files
```

使用自己的 GitHub 账号完成 Git 登录。每个本地副本均检查提交身份；如果未设置，在仓库目录内设置本人使用的名字和 GitHub 已验证邮箱或 GitHub 提供的 noreply 邮箱，不要照抄别人的身份：

```sh
git config user.name
git config user.email
```

仓库级配置的命令形式是 `git config --local user.name "你的名字"` 和 `git config --local user.email "你的提交邮箱"`。把说明文字替换成真实值再运行。

验收：`git lfs ls-files` 列出 `test-tone.wav`；本地音频有 RIFF 文件头且可播放，不是只有三行文字的 LFS 指针。音频很短，音量保持较低即可。

## 1. 两人分别做一个任务

你从最新主分支开始：

```sh
git switch main
git pull --ff-only
git switch -c task/you-first-change
```

用文本编辑器修改 `practice/you.txt`，写下“我已完成第一次提交”。保存后：

```sh
git diff
git add practice/you.txt
git commit -m "practice: complete my first change"
git push -u origin task/you-first-change
```

朋友使用同样流程，但分支为 `task/friend-first-change`，修改和提交 `practice/friend.txt`。练习时不要互相修改对方的文件。

两人分别在 GitHub 创建自己的 Pull Request，目标分支选 `main`，检查 Files changed 是否只有预期文件。

先合并其中一个任务。第二人随后在自己的任务分支执行：

```sh
git fetch origin
git merge origin/main
git push
```

确认文件内容正确，再合并第二个 Pull Request。可采用 GitHub 默认的合并方式；本练习不强制 squash 或另一人审批。

两人均回到主分支并更新：

```sh
git switch main
git pull --ff-only
```

验收：双方电脑上的 `you.txt`、`friend.txt` 都包含对应改动，`git status` 干净。工作区有尚未保存或提交的内容时先处理它们，再切换分支或更新。

## 2. 再做一次真正的“代码”修改

任选一人创建 `task/player-speed` 分支，在 `game/samples/PlayerSettings.cs` 把 `MoveSpeed` 从 200 改为 240；按上一步提交、推送、创建 Pull Request、合并。另一人更新 `main` 并确认数值为 240。

这个文件只用于展示 C# 文本差异，当前没有构建或运行游戏的验收。

## 3. LFS 文件锁与资产交接

一人从最新主分支创建 `task/audio-handoff`，先查看现有锁并取得音频锁：

```sh
git lfs locks
git lfs lock game/assets/audio/test-tone.wav
```

另一人运行 `git lfs locks`，应看到该文件已被占用；再尝试同一路径的 `git lfs lock`，预期失败。不要强制解锁或绕过只读属性。首次验证也检查两人的客户端是否启用了 LFS 推送时的锁检查；文件锁本身不是不可绕过的服务端写保护。

持锁人可以用自己已有的音频编辑器，对示例做一次很小的修改并保存为有效 WAV，例如降低音量；也可用另一段无版权问题的短 WAV 替换。不要把文本文件改名成 WAV。

```sh
git add game/assets/audio/test-tone.wav
git commit -m "practice: update LFS audio asset"
git push -u origin task/audio-handoff
git lfs ls-files
```

通过 Pull Request 合入主分支；确认上传和合并完成后释放锁：

```sh
git lfs unlock game/assets/audio/test-tone.wav
```

另一人回到 `main` 更新，并取得 LFS 文件：

```sh
git pull --ff-only
git lfs pull
```

验收：另一人能播放更新后的音频，锁列表不再显示旧占用。Git 页面显示音频由 LFS 保存，但网站上不一定提供音频预览。你们后续可用一个真实 `.blend` 重复此流程。

## 4. 可选：故意练习一次文本冲突

先结束其他任务、保持工作区干净。双方从同一个最新 `main` 各建任务分支，分别修改 `practice/shared.txt` 的同一行并提交。

第一人合入自己的 Pull Request；第二人在自己的任务分支执行 `git fetch origin`、`git merge origin/main`，此时应出现冲突。

第二人打开 `practice/shared.txt`，根据两人的真实意图保留最终内容，删除冲突标记，然后运行：

```sh
git add practice/shared.txt
git commit -m "practice: resolve shared text conflict"
git push
```

检查 Pull Request 后再合并。若暂时不想处理本次合并，且合并前工作区干净，可用 `git merge --abort` 退回合并前的任务分支。

本练习只证明文本冲突处理；不要把这种手工编辑方式套用到 `.blend` 等二进制文件。Godot 场景即使是文本格式，也需要在编辑器中检查合并后的结构。

## 5. 在新的目录恢复一次

任选一人另找一个空的父目录，把同一仓库克隆为新的 `gamejam-recovery-check` 目录。保留原副本，不删除它。

```sh
git clone https://github.com/fenglinr/gamejam-collab-sandbox.git gamejam-recovery-check
cd gamejam-recovery-check
git lfs install --local
git lfs pull
git status
git lfs fsck
```

检查两人的练习记录、C# 数值和更新后的 WAV；这样验证恢复依赖远端仓库，而不是某台电脑未提交的文件。

## 完成清单

- [ ] 两人各自使用本人账号和独立本地副本。
- [ ] 两人的提交都合入 main，另一方能取得。
- [ ] C# 文本差异和合并流程已走通。
- [ ] LFS 音频可取得、可播放。
- [ ] 远端文件锁能被另一方看到，重复取锁失败。
- [ ] 修改后的 LFS 音频已由另一方取得。
- [ ] 从全新目录克隆后，文字和音频仍完整。
- [ ] 若完成冲突练习，双方能解释如何处理和如何取消当前合并。

这些通过后再添加最小 Godot C# 项目和真实 Blender 文件，验证引擎导入、运行、源文件依赖及导出；当前仓库不代表那些环节已经通过。
